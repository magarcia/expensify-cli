# Authentication

The CLI uses a New Expensify device session. Your device credentials obtain an `authToken`; the CLI sends that token with API requests. This is the app's authentication mechanism, not an OAuth device-code flow.

## Log in

Run login from your terminal:

```sh
expensify auth login
expensify auth status --check
```

The CLI opens New Expensify in an installed Chrome-compatible browser. Sign in there, including any email code or other verification your account requires. Once you're authenticated, the CLI reads the app's device credentials, verifies them with Expensify, and saves them in your OS keyring when available. You don't need to open developer tools or copy secrets.

Browser login supports Chrome, Chromium, Microsoft Edge, and Brave. Choose one by name or give its executable path:

```sh
expensify auth login --browser chrome
expensify auth login --browser /path/to/chromium
expensify auth login --login-timeout 10m
```

`--browser` accepts `auto`, `chrome`, `chromium`, `edge`, `brave`, or an executable path. Safari and Firefox aren't supported for automatic capture. If either is your default browser, use an installed supported browser or one of the import options below.

Login waits up to five minutes. `--login-timeout` changes this sign-in window; the global `--timeout` still controls individual API requests and defaults to `30s`. Closing the login browser or interrupting the CLI cancels login.

The CLI starts its own temporary browser profile. Your usual browser profile stays separate, so you'll sign in again even if you're already logged in elsewhere. The CLI closes the browser it started and removes that temporary profile when login ends. It uses a local Chrome DevTools connection to read New Expensify's storage. This isn't an OAuth redirect or callback flow. Chrome requires a separate data directory for remote debugging, as described in [Chrome's documentation](https://developer.chrome.com/blog/remote-debugging-port).

## Manual login and imports

To paste credentials at hidden prompts:

```sh
expensify auth login --manual
```

Get the pair from an authenticated New Expensify session. In your browser's developer tools, inspect the app's stored credentials for `autoGeneratedLogin` and `autoGeneratedPassword`. Their storage location can change with the app. The CLI calls these values `partnerUserID` and `partnerUserSecret`.

You can also import a private JSON file:

```sh
expensify auth login --credentials-file /private/path/expensify-device.json
```

The file can contain this shape. Replace the placeholders in a private editor:

```json
{
  "partnerUserID": "DEVICE_LOGIN",
  "partnerUserSecret": "DEVICE_SECRET"
}
```

The importer also accepts the app's `autoGeneratedLogin` and `autoGeneratedPassword` names, an object under `credentials` or `session`, or a legacy `DEVICE_SESSION_CREDENTIALS` object or JSON string. An `authToken` is optional when you supply both device credentials.

For a secret manager or another process, pass JSON through stdin:

```sh
expensify auth login --credentials-stdin < /private/path/expensify-device.json
```

The CLI never accepts a secret as a command-line flag. Keep credential files outside this repository and restrict access to your account.

File, stdin, and environment credentials don't open a browser. With no credentials, `--no-input` prevents implicit browser login and prompts. An explicit `--browser` starts browser login even with `--no-input` or piped output; a person still needs to complete sign-in in that browser.

## Session lifetime

There's no verified, fixed expiration duration for either the session token or the device credentials.

If Expensify returns `jsonCode: 407`, the CLI exchanges the device pair for a new token, saves it when using stored credentials, and retries the original request once. A saved device pair can therefore keep the CLI usable after its session token expires. It doesn't guarantee permanent access: Expensify can revoke or reject the device credentials.

An `authToken` alone works until Expensify rejects it. Without a device pair, the CLI can't refresh it. Import fresh credentials when authentication fails.

## Environment credentials

These variables override saved credentials:

| Variable | Purpose |
| --- | --- |
| `EXPENSIFY_AUTH_TOKEN` | Existing session token |
| `EXPENSIFY_PARTNER_USER_ID` | New Expensify device login |
| `EXPENSIFY_PARTNER_USER_SECRET` | New Expensify device secret |

Set both device variables together. Environment credentials form a separate account context: the CLI won't combine an environment token with a saved account's device pair. Supplying a device pair permits renewal during the command.

Inject these variables from your secret manager or CI secret store. Avoid literal secrets in shell commands or shell history.

Resource commands keep environment credentials and renewed tokens in memory; they don't save them. An explicit `auth login` verifies and saves the supplied credentials using the selected storage backend.

## Local storage

The CLI prefers your OS keyring through [zalando/go-keyring](https://github.com/zalando/go-keyring): macOS Keychain, Windows Credential Manager, or a Linux Secret Service keyring over D-Bus. The library requires no C bindings. On macOS, it uses the system's `/usr/bin/security`; Linux needs an available Secret Service and login collection.

Keyring entries use the service `expensify-cli` and an account derived from the absolute configuration directory. Each configuration directory has separate credentials. Change the directory with `--config-dir` or `EXPENSIFY_CONFIG_DIR`.

Choose storage with `EXPENSIFY_CREDENTIAL_STORE`:

| Value | Behavior |
| --- | --- |
| `auto` (default) | Prefer the OS keyring; use the private plaintext file when the keyring is unavailable. |
| `keyring` | Require the OS keyring; fail instead of falling back to plaintext. |
| `file` | Use only the private plaintext file. |

The fallback file is `$XDG_CONFIG_HOME/expensify/credentials.json`, or `~/.config/expensify/credentials.json` when `XDG_CONFIG_HOME` isn't an absolute path. It contains the session token, device credentials, and optional account metadata. Nonsecret settings remain in `config.json`.

In `auto` or `keyring` mode, existing credential files migrate to the keyring when available. The CLI writes the keyring entry before deleting the file. If the keyring write fails, `auto` retains the private file; `keyring` reports an error. A failed cleanup reports an error so you can retry.

On macOS and Linux, the CLI creates its directory with mode `0700` and writes credentials atomically with mode `0600`. On Windows, it creates protected access control lists restricted to your account and accepts existing storage owned by your account with grants only to you, SYSTEM, and Administrators. It rejects storage accessible to other users and symbolic links.

The fallback file contains plaintext secrets protected by filesystem permissions. Use `EXPENSIFY_CREDENTIAL_STORE=keyring` when plaintext storage is unacceptable.

`expensify auth status` reports the credential source and `storage` (`keyring`, `file`, `none`, or `environment`) without revealing secrets. `path` identifies the credential file only when using file storage. Login also reports its storage backend. Add `--check` to status to verify access with Expensify.

```sh
expensify auth logout
```

Logout removes both the keyring entry and any fallback file for the selected configuration directory. If the keyring is unavailable, logout reports an error; retry when it is available to finish removing stored credentials. In `file` mode, logout removes only the file. Clear any injected environment credentials separately. Local logout doesn't revoke the browser's device session at Expensify.

## API compatibility

This CLI calls New Expensify's app API. It isn't an official Expensify client, and these endpoints can change without a public compatibility promise. Integration Server partner credentials are a different authentication system and won't work as this device pair.

The authentication approach follows the public [Expensify app source](https://github.com/Expensify/App) and the [Printing Press Expensify client](https://github.com/mvanhorn/printing-press-library/tree/main/library/productivity/expensify). The implementation and tests in this repository define the CLI's behavior.
